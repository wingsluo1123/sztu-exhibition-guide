现场按步骤操作请先看 [自研自主导航现场运行手册](autonomous_navigation_runbook.md)。本文件后续内容主要保存诊断记录、参数背景和历史验证证据。

当前导航使用自研 FAST-LIO + Nav2 + AMCL；厂商 SLAM 不参与。

2026-10-14 场地安排：已选用地图保存为“展厅图” `maps/exhibition/map.yaml`，用于最终落地。
“教室图” `maps/classroom/map.yaml` 已于 2026-10-14 独立生成，用于点位标定、定位、路径规划和避障测试；测试点位尚未标定。
旧 `config/waypoints.yaml` 对应 `maps/testroom`，不能用于展厅或教室；各场地点位需在对应地图上重新选取并校验。
教室地图现场核对后按以下顺序验证，保持 `live:=false`。

已确认悬吊或支撑固定的运控测试单独使用 `docs/restrained_drive_trial.md`。
该入口只做单次前进指令与零速回读，不执行路线，不替代地面停车或周向感知验收。

## 启动顺序

1. 停掉会抢速度的旧服务：

   ```bash
   systemctl --user stop sztu-bridge
   ```

2. 终端一启动实时里程计和点云（保持运行）：

   ```bash
   cd ~/sztu
   source /opt/ros/humble/setup.bash
   source install/setup.bash
   tools/run_lio_live.sh --bridge --local-odom
   ```

   Nav2/AMCL 每趟使用静止初始化得到的局部重力基准；不要传 `--map-frame` 或复用旧地图的 `sztu_up`。FAST-LIO 每次重启的原点和重力坐标基准不保证与建图时一致，地图中的位置与朝向由 AMCL 对齐。

3. 教室图生成后，终端二启动已知地图导航（默认 `live:=false`，不会发硬件指令）：

   ```bash
   cd ~/sztu
   source /opt/ros/humble/setup.bash
   source install/setup.bash
   ros2 launch sztu_navigation autonomous.launch.py \
     map:="$HOME/sztu/maps/classroom/map.yaml" \
     live:=false
   ```

   展厅验证时将地图参数换为 `map:="$HOME/sztu/maps/exhibition/map.yaml"`，并使用展厅自己的点位。

4. 在开发机桌面终端打开导航显示：

   ```bash
   cd ~/sztu
   bash tools/watch_navigation.sh
   ```

   此脚本使用项目 DDS 配置并拒绝重复启动 RViz；保留现有显示设置。已有窗口时先关闭，当前会话由服务托管的窗口可执行 `systemctl --user restart sztu-rviz.service`。如果关闭窗口后进程仍在，不要不断另开窗口；先检查卡住的 RViz 进程。

   脚本同时管理 `rviz_tf_relay.py`：以 Best Effort 接收远端 `/tf`，只将 `map → sztu_nav_odom → sztu_nav_base` 两段原始变换转发至 `/sztu/rviz_tf`，供本机 RViz 可靠订阅。时间戳及位姿不变，没有重复发布到机器人使用的 `/tf`；`/tf_static` 保持原订阅。任一子进程退出时关闭另一进程，避免转接失效后留下孤立窗口。此显示入口仅覆盖当前导航视图，不提供完整机器人关节 TF。

   开发机 UDP 接收缓冲上限需至少 8 MB，否则项目 DDS 配置的接收缓冲会被内核截断。脚本会在不足时提示；可执行 `sudo sysctl -w net.core.rmem_max=8388608` 后重启 RViz。此调整仅当前开机有效，不修改机器人时钟或测量时间戳。

   无线开发机可用 `iwconfig` 查看当前网卡省电状态。本现场网卡为 `wlp4s0`，临时关闭省电命令是 `sudo iwconfig wlp4s0 power off`，恢复为 `power on`；不需要断开网络。重新连接或重启后可能由 NetworkManager 恢复默认值。此操作不能保证消除 Wi-Fi 抖动，也不能代替时效验证。

   在 RViz 设置一次 `/initialpose`，必须是机器人当前在选用地图中的真实位置和朝向。等 `/amcl_pose` 协方差稳定并确认雷达贴图后，再进行 `live:=false` 的规划验证；讲解任务须等待新图点位完成标定和校验。

   保持机器人静止，用工具栏的 `2D Pose Estimate` 在实际位置按下鼠标，沿机器人朝向拖出箭头后松开。设置一次后观察，不要连续重复设置。定位正确还需确认雷达点与地图墙面重合；低协方差本身不能证明位置正确。重启 FAST-LIO 或 AMCL 后需要重新设置。

   只重启 RViz 不需要重设初始位置。`AMCL Pose` 显示使用 `Reliable` / `Transient Local`，可获取 AMCL 保留的最后一条位姿；箭头显示出来不代表该位姿仍然新鲜，仍须确认实时雷达点和定位持续更新。

   切换 Wi-Fi 后若 SSH 可达、机器人节点仍在运行，但开发机收不到 `/map`，检查机器人 `ss -unap` 中导航进程是否仍绑定旧 IP。2026-10-10 实测导航进程保留了 `192.168.208.19`，切到 `192.168.43.4` 后重启 RViz 无法恢复；保存新鲜位姿、保持静止、仅重启自研导航栈后通信恢复。恢复位姿前须确认 FAST-LIO 未重启且里程计未明显变化；否则重新设置真实位置。不要为此重启厂商服务。

   同日 RViz 被 `SIGKILL` 终止后，重新启动仍可能只显示箭头而没有地图。该次 IP 正确，抓包发现约 65 KB UDP 数据报被拆成大量 IP 分片，开发机重组失败计数持续增长。`autonomous.launch.py` 仅为 `map_server` 使用 `fastdds_map_wifi.xml`，由 DDS 对地图进行分片和可靠重传。2026-10-11 已修正该配置：传输层 `maxMessageSize` 保留 65500 字节接收能力，仅通过发布端 `fastdds.max_message_size=1400` 限制发送报文。此前将传输层也设为 1400，会截断其他节点发来的大报文，不能继续使用。点云接收和 FAST-LIO 的共享内存配置不变。修改后需重新构建 `sztu_navigation` 并重启自研导航栈；静止恢复已保存位姿时，先等 AMCL 生命周期状态为 `active`，再发布初始位姿，避免启动期间丢失。

   开发机与真机构建通过；隔离域 42 验证完整地图传输后，真机部署验证 RViz 重启约 5 秒收到 613×463 地图，独立新订阅者也收到地图、扫描、AMCL 和局部代价地图。排查期间临时调整的开发机内核网络参数已恢复原值。该修复针对地图传输，不能证明 Wi-Fi 下所有实时扫描没有延迟；`SIGKILL` 的发起原因也尚未确定。当前 RViz 由用户服务管理，可用 `systemctl --user restart sztu-rviz.service` 重启窗口，无需重启 FAST-LIO 或重复设置箭头；此服务是本次会话创建的临时服务。
