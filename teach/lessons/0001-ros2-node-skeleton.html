Lesson 0001 · 地基

一个 Python 类，怎么变成能跑起来的 ROS2 节点

读懂本项目里最短的一个节点 —— emotion_controller.py（约 60 行）—— 你就掌握了全项目所有节点共用的那副骨架。

为什么先学这个 你的目标是能独立改代码 / 加功能。但无论你想加一条指令、改一段导航、还是修个 bug，第一步都得先看懂"这段代码是怎么被 ROS 跑起来的"。这副骨架就是那把钥匙 —— 本项目 10 个节点全是它的变体。

一、先看完整的一个节点

这是 src/sztu_interaction/sztu_interaction/emotion_controller.py 的结构（去掉了业务细节，只留骨架）。全项目每个节点都长这个样子：

# ① 导入 rclpy 和 Node 基类
import rclpy
from rclpy.node import Node
from aimdk_msgs.srv import PlayEmoji   # 这个节点要用的服务类型

# ② 定义一个类，继承 Node
class EmotionController(Node):
    def __init__(self):
        super().__init__('emotion_controller')   # ③ 给节点起名

        # ④ 声明这个节点要用的 ROS 接口
        self.emoji_client = self.create_client(
            PlayEmoji, '/aimdk_5Fmsgs/srv/PlayEmoji')

    # ⑤ 节点自己的能力，做成普通方法
    def show_emotion(self, emotion):
        ...
        future = self.emoji_client.call_async(request)
        rclpy.spin_until_future_complete(self, future, timeout_sec=2.0)
        ...

# ⑥ main：把节点跑起来的固定套路
def main(args=None):
    rclpy.init(args=args)          # 启动 ROS 运行时
    node = EmotionController()      # 建节点（会执行上面的 __init__）
    try:
        rclpy.spin(node)            # 交出控制权，等回调
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

二、六个部件，逐个说清

  1. 继承 Node：class EmotionController(Node) 让你的类"是一个"ROS 节点，自动拥有 create_client、get_logger、create_timer 等一整套能力。你几乎从不直接 new 一个 Node，而是继承它。
  2. super().__init__('名字')：这行把节点注册进 ROS 网络，用的名字就是别人 ros2 node list 看到的名字。名字必须唯一 —— 这也是为什么 bridge_server 把三个控制器塞进一个进程后，绝不能再单独启动它们（会重名冲突）。
  3. 声明式接口：create_publisher / create_subscription / create_client / create_timer。注意关键词——声明。你只是登记"我要用这个 topic/service"，并不是马上执行。真正干活发生在回调里。
  4. 能力=普通方法：show_emotion() 就是个普通 Python 方法，内部用第③步登记的 emoji_client 去调服务。你加功能，绝大多数时候就是在这里加一个方法。
  5. main() 的四步套路：init → 建节点 → spin → shutdown。这四行几乎逐字出现在每个节点文件末尾，是模板，不用背，认得出即可。
  6. entry_points 注册：setup.py 里写 'emotion_controller = ...emotion_controller:main'，才让 ros2 run sztu_interaction emotion_controller 能找到这个 main。改了入口要重新 colcon build。
关键心智模型 __init__ 里声明接口（一次性、开机时），方法和回调里使用接口（反复、运行时）。rclpy.spin(node) 是那句"我准备好了，开始处理事件吧"—— 在它之前一切都是布置，在它之后节点才真正活着响应。

三、spin 到底在干嘛？

这是新手最容易含糊的一点。rclpy.spin(node) 会阻塞在这里不返回，进入一个循环：不停地检查"有没有我订阅的消息到了 / 有没有定时器该触发了 / 有没有服务响应回来了"，有就调用对应的回调函数。

所以节点的运行模式是事件驱动的：你不主动轮询，而是登记好回调，然后 spin 替你等。emotion_controller 作为一个纯服务调用节点，甚至可以不 spin——它的 main 里有个分支：命令行带参数时直接调一次 show_emotion 就退出，不带参数才 spin 当常驻服务。

对照真实代码 打开 src/sztu_interaction/sztu_interaction/emotion_controller.py，从头到尾对一遍上面六个部件。它只有 60 行，是全项目最干净的样本。看完再瞄一眼 tts_controller.py——你会发现同一副骨架，只是多了重试逻辑。这就是"读懂一个=读懂一类"。

四、检索练习

合上上面的内容，凭记忆答。答错没关系——正确答案会即时高亮并解释，这种"努力回忆"正是记得牢的关键。

1. super().__init__('emotion_controller') 这一行最主要做了什么？

它调用父类 Node 的构造，用给定名字把节点注册进 ROS 图。启动事件循环是 rclpy.spin（C），调服务是 show_emotion（A），都不在这一行。

2. 你想给这个节点加一个"重置表情"的新能力，最该改哪里？

节点的能力就是类里的方法（第④/⑤部件）。实际上 emotion_controller.py 已经有一个 reset_emotion() 方法，它就是调 show_emotion('neutral')——正是这个模式。

3. 为什么 bridge_server 内部持有三个控制器后，就不能再单独 ros2 run 启动它们？

每个控制器 __init__ 里都 super().__init__('tts_controller') 等固定名字（第②部件）。同名节点在同一 ROS 网络里冲突。这正是 remote.launch.py 注释反复强调"不要重复启动"的原因。
