### 数据从哪里来

雷达测量周围物体表面，在一帧中提供一组采样点，称为点云。它不是占据栅格地图，
也不是机器人位置；后续算法需要结合多帧点云和运动信息，才能估计位姿、累积地图。
发布程序还可能包含强度、逐点时间等附加信息，本步尚未解析字段或验证其质量。

厂商官方资料：
https://x2-aimdk.agibot.com/zh-cn/latest/example/Python.html#py-echo-lidar-data

既有传感器驱动将数据发布到 /aima/hal/sensor/lidar_chest_front/lidar_pointcloud，
消息类型是 sensor_msgs/msg/PointCloud2。话题名是厂商接口约定，类型是 ROS 标准定义。
本例只订阅已经运行的驱动，不调用旧项目的建图导航包；未查明驱动的具体发布进程归属。

### 核心代码与字段

```python
from sensor_msgs.msg import PointCloud2


def receive_cloud(message):
    point_count = message.width * message.height
    node.get_logger().info(
        f'frame={message.header.frame_id}, '
        f'stamp={message.header.stamp.sec}.{message.header.stamp.nanosec:09d}, '
        f'points={point_count}'
    )
```

- sensor_msgs 是 ROS 2 提供的传感器消息包，PointCloud2 是其中的消息类型，规定点云存放结构。
  它不是驱动，不会自己测量或启动雷达；导入只是让 Python 能使用这个消息类。
- message 是 ROS 在订阅收到数据后传入 receive_cloud 的 PointCloud2 对象。
- width、height 是 PointCloud2 定义的字段，描述点云的列数与行数；乘积为记录的点条目数量。
  无组织点云通常 height=1；点条目数不等于不同物体数量，也不保证每个点有效。
- header 是 PointCloud2 的 Header 信息头，frame_id 是发布者填写的点坐标参考系名字。
- 本次实际 frame_id 为 lidar_chest_front：表示点坐标相对于胸前雷达坐标系，
  不能直接视为 map 中坐标。字符串本身不会创建 TF，也不证明外参正确。
- header.stamp 是发布者附带的时间戳，sec 与 nanosec 分别为整数秒与纳秒部分。
  格式 :09d 将纳秒部分显示为九位，前面补零；不是精度测量结果。
  本步观察到时间戳变化，未验证它是否准确对应采集时刻或和 IMU 同步。
- 真正每个点的内容在消息的 data 中，由 fields 等字段描述布局；本步没有读取或解析它。

订阅注册使用：

```python
subscription = node.create_subscription(
    PointCloud2,
    '/aima/hal/sensor/lidar_chest_front/lidar_pointcloud',
    receive_cloud,
    qos_profile_sensor_data,
)
```

四个参数依次是类型、话题名、回调函数、通信配置。qos_profile_sensor_data 来自 rclpy.qos，
使用 BEST_EFFORT、VOLATILE、KEEP_LAST 深度 5，与厂商示例选用的传感器通信设置一致。
BEST_EFFORT 不要求补齐每一条丢失消息；本次不是通信策略专题，先认识所用配置及其来源。

数据流：机器人雷达 → 已有驱动发布 PointCloud2 → 我们的订阅回调 → 读取元数据 → 日志。

### 本步补充：QoS 配置的来源和含义

`from rclpy.qos import qos_profile_sensor_data` 导入 rclpy 预先创建的通信配置对象，
不是函数或消息类型，使用时不加括号。QoS（Quality of Service）描述消息传递规则，
不修改点云坐标或消息的数据结构。

- BEST_EFFORT：尽力传递，不要求把每条丢失消息补齐。
- VOLATILE：不要求发布端为后来加入的订阅者保存此前消息。
- KEEP_LAST、深度 5：历史缓存保留最近最多五条的设置，不是五帧每秒，也不是收到五帧就停。
- 该配置适合本次参考的厂商传感器示例，但不保证无丢帧或无延迟。
- 发布端和订阅端的 QoS 要兼容；BEST_EFFORT 发布不能满足 RELIABLE 订阅要求。
  相同话题名与类型并不保证建立数据连接。
- create_subscription 最后传整数 10 的简写采用该深度及其他默认设置，
  不等同于 qos_profile_sensor_data。

复述反馈：学习者理解点云尚未建立雷达/机器人与地图之间的位置关系，
frame_id=lidar_chest_front 表示相对于雷达；并正确说明深度 5 不是接收频率，
QoS 描述传递规则。本步复述完成，等待继续指令。

## 第 2 步：读取雷达自带 IMU

IMU（惯性测量单元）提供角速度、加速度等惯性测量；本步读取雷达内置 IMU，
不是胸部或其他独立 IMU。输入来自既有传感器驱动，接口依据用户提供的官方示例。

- 话题：/aima/hal/sensor/lidar_chest_front/imu。
- ROS 标准类型：sensor_msgs/msg/Imu，由 sensor_msgs 包提供 Python 消息类 Imu。
- 电脑源码：lesson06_imu_reader.py，机器人副本：/home/agi/sztu_learning/lesson06_imu_reader.py。
- 与点云一样采用 qos_profile_sensor_data；只读，没有启动驱动、定位或控制运动。

核心读取：

```python
angular = message.angular_velocity
acceleration = message.linear_acceleration
```

message 是收到后由 ROS 传入的 Imu 对象；angular_velocity、linear_acceleration 是标准消息字段，
类型都是含 x、y、z 三个数的 Vector3。angular、acceleration 是本函数给它们取的局部变量名，
不在这里计算或复制测量数据。

- angular_velocity：绕各坐标轴的角速度，单位 rad/s，不是朝向角，也不是轮子速度。
- linear_acceleration：各轴加速度测量，单位 m/s²，不是位置或速度；原始加速度计通常含重力影响。
- header.frame_id：两个向量所用参考系的名称，本次为 lidar_imu_chest_front。
  不直接等于上一轮点云的 lidar_chest_front，更不能假设这些轴就是机器人前、左、上。
- 角速度和加速度帮助 FAST-LIO 估计帧间运动、处理运动期间的点云；并不是把 IMU 直接积分就能得到可靠地图定位。
- 本步不使用 orientation 字段，也不假设 IMU 一定提供有效的绝对朝向。

## 第 3 步：把点云和 IMU 录成 rosbag

rosbag 是 ROS 的消息录制/回放机制。录制器像订阅节点一样接收指定话题，
将消息及相关类型、时间等信息保存到磁盘；不是视频录像，不保存正在运行的算法或整个系统。
本步只录制两个原始传感器话题，没有 TF，不是完整建图数据集。

【机器人：SSH 终端，先 source /opt/ros/humble/setup.bash】本次执行的核心命令：

```bash
ros2 bag record -s sqlite3 -o /home/agi/sztu_learning/bags/lesson03_lidar_imu_01 \
  /aima/hal/sensor/lidar_chest_front/lidar_pointcloud \
  /aima/hal/sensor/lidar_chest_front/imu
```

- ros2 bag record：启动消息录制器，不启动传感器驱动或建图算法。
- -s sqlite3：明确使用 SQLite 存储插件，生成 .db3 数据库文件。
- -o 后为输出目录，不是 Python 文件；录制器新建该目录，不应覆盖已有录制。
- 最后两个参数指定要订阅保存的话题，包含点云、IMU，不会自动录所有话题。
- 行末反斜杠让 Bash 把多行当作一条命令；反斜杠后面不要再加空格。
- 人工使用时 Ctrl+C 停止并等待写盘结束，不是关闭机器人驱动。

本次为限定时长，外层实际加了 timeout --signal=INT --kill-after=5s 5s：
五秒后给录制器发送 SIGINT 请求结束，124 是 timeout 的返回码，不是普通成功退出码。
启动发现、订阅等待占用时间，所以命令运行五秒不等于文件一定含五秒数据。
远端目录由本次任务创建，未改已有录制或服务，未控制机器人运动。

## 第 7 步：发布假设的静态 TF

文件 lesson08_static_tf.py 复用上一步的假设关系，新增 ROS 节点和 StaticTransformBroadcaster。
静态指两个坐标系之间的相对关系不随时间改变，不表示机器人在世界中不能运动。
StaticTransformBroadcaster 来自 tf2_ros，负责把 TransformStamped 包装为 TF 消息发布到 /tf_static。
其 TRANSIENT_LOCAL 持久性使发布者仍存活时，兼容的晚加入订阅者也能接收保留的关系。
不需要自己为该关系创建定时器，不等同于永久保存至磁盘；保留 spin 维持节点和发布者存活。

核心新语句：
```python
broadcaster = StaticTransformBroadcaster(node)
transform.header.stamp = node.get_clock().now().to_msg()
broadcaster.sendTransform(transform)
```

node.get_clock() 取得节点时钟；now() 读取当前时刻；to_msg() 将其转换为 header.stamp
需要的 ROS 时间消息。sendTransform 才实际发送，创建消息或赋值本身不会发送。


## 第22步补讲：求逆实现与验证语句

已逐步解释 Rotation.from_quat(quaternion).as_matrix()：从xyzw四元数生成旋转矩阵，
只换表示、不求逆；rotation.T 为转置，对合法旋转矩阵即逆旋转。
NumPy转置通常为共享数据视图，本脚本不修改其元素。
inverse_translation = -(inverse_rotation @ translation)：先将原位移换至IMU轴表达，
再反转位移方向，得到雷达原点在IMU中的位置；@是矩阵乘法。
学习者最初将不能直接取负归因于“因为是矩阵”，并误认为轴同向也不能取负，

后续核对实际脚本尾部：
```python
assert np.allclose(inverse_rotation @ rotation, np.eye(3))
assert np.allclose(inverse_rotation @ translation + inverse_translation, 0)
```
np.eye(3) 是3×3单位矩阵，代表不改变向量的旋转；逆旋转乘原旋转应回到该关系。
np.allclose 对数组各元素做近似比较，容许浮点计算误差；不是逐元素绝对相等，
其默认容差仅用于本次数值计算自检，不代表允许的真机标定误差。
第二行检查正反变换的平移部分相互抵消，各分量接近0。

复用lesson20_create_cloud.py，本轮不增加程序。重跑退出0，仍显示point_step22、data22字节。
FLOAT32=32位=4字节；UINT16=16位=2字节（1字节8位）。
本例x/y/z/intensity/time共5项FLOAT32，占20字节；ring占2字节，总22字节。
PointField(name='ring',offset=20,datatype=PointField.UINT16,count=1)
表示ring从偏移20开始，占20、21两个字节，因此下一条点记录可从22开始。
这份自建紧凑布局没有额外填充，不应据此认为所有PointCloud2都是紧凑布局。
真实雷达timestamp为FLOAT64而不是本例time的FLOAT32，且存在填充，所以原始point_step32，
不能只凭点记录字节数不同判定消息错误。
point_step为相邻点记录的字节跨度，row_step为相邻行的字节跨度，len(data)=row_step*height；
一般有组织点云可能有行填充，不泛化为任意消息都等于width*height*point_step。
本例create_cloud生成一行1点，因此data为22字节；若同布局一行2点则为44字节。
本步仅理解布局，不宣称FAST-LIO/PCL兼容性已通过，未发布消息或操作真机。

### 第65步补充：HEIGHT是点数据的排列行数

### 第66步补充：把tf_frame改成base_link会发生什么

复述两题均正确：重复发布的是旧扫描，改tf_frame不会变换XYZ。学习者追问修改后的实际含义，停留本步解释。

却声明其属于base_link；没有根据真实变换计算该点在base_link下的坐标。
若RViz Fixed Frame仍camera_init，它会尝试查找相应消息时刻base_link到camera_init的TF。

若连Fixed Frame也改为base_link，消息与显示参考系同名，可直接显示，但画面可见不证明坐标表达正确。
只有两个坐标系实际重合等特殊情况，原数值才可能同时成立；本例没有这样的实测依据。
正确方式为保持frame_id与原始坐标含义一致；确需转为base_link时，先用有依据的实际变换计算新XYZ，再标记目标坐标系。

实际文件lesson46_reliable_relay.py，第30行receive_cloud(message)：

```python
def receive_cloud(message):
    points = point_cloud2.read_points(message, field_names=names)
    values = [
        (point['x'], point['y'], point['z'], point['intensity'],
         offset_to_seconds(point['timestamp'], ASSUMED_TIMESTAMP_UNIT), point['ring'])
        for point in points
    ]
    candidate = point_cloud2.create_cloud(message.header, fields, values)
    publisher.publish(candidate)
```

message是这一帧原始PointCloud2；通常一帧有很多点。point_cloud2来自ROS库sensor_msgs_py。
names是文件前面定义的输入字段名列表：x、y、z、intensity、ring、timestamp。
read_points按消息本身的字段布局解析数据，返回points，可逐点按字段名取值；不进行坐标变换。
point是遍历时当前一个点，values是新建的列表，每个元素为按输出字段顺序排列的一个点的数值元组。
输出顺序为x、y、z、intensity、time、ring；XYZ、强度和ring原样取值，
timestamp经自写辅助函数offset_to_seconds换算数值，放在输出time字段。
offset_to_seconds来自lesson28_time_unit.py，ns换算为秒就是乘1e-9；
ASSUMED_TIMESTAMP_UNIT='ns'仍是候选假设，转换程序本身不能证明真机单位或计时起点正确。

假设单点输入x=1、y=2、z=0.3、intensity=10、ring=4、timestamp=80000000，且单位按ns处理，
则values中对应元素为(1, 2, 0.3, 10, 0.08, 4)。该例是教学假设，不是真机采样。
fields也是前面创建的变量，保存输出各字段的名称、类型、字节位置；本轮重点是字段排列顺序。
create_cloud用原message.header、输出格式fields和所有新点值values构造新的PointCloud2，
返回给candidate；本例time以FLOAT32存储，0.08为近似表示。
message.header保留原帧时间和坐标系名称；点内timestamp转换与帧header时间是两件事。
最终publisher.publish(candidate)才发布。此处只重建格式与候选时间单位，不计算机器人位姿、

### 2026-11-20：xyz_bytes后半段——跳过无效点并返回字节

继续已有lesson44_collect_mapping.py第21～22行；运行位置为电脑离线。
前两行已将这一帧XYZ排列成每行一个点、每值4字节的小端浮点数组xyz。

```python
valid = np.isfinite(xyz).all(axis=1)
return xyz[valid].tobytes(), int(valid.sum()), int((~valid).sum())
```

np.isfinite逐个坐标判断是否为有限数，NaN（无效数值）和正负无穷判为False，
普通有限坐标（包括负数与0）判为True，不据此判断点是否为物理噪声或地图正确。
all(axis=1)在每一行的三个布尔值上求全部为True，每点最终得到一个是否保留的标记。
例如教学假设xyz=[[1,2,3],[4,NaN,6],[7,8,9]]，
isfinite结果为[[True,True,True],[True,False,True],[True,True,True]]，
valid为[True,False,True]。只要XYZ任一坐标非有限，就跳过整个点，不能只删除一项破坏XYZ对应关系。
xyz[valid]以布尔数组选行，得到第1、3点，不改原xyz。
tobytes()将有效点的数值按当前数组顺序复制为bytes，不是数字文本，不包含PCD头，且尚未写文件。
valid.sum()按True=1、False=0累计保留点数；~valid翻转布尔标记后sum累计跳过点数；
int将NumPy计数结果转为Python整数。当前例返回24字节点数据、2个有效点、1个跳过点。
辅助函数调用处data,count,skipped=xyz_bytes(message)对应接收这三个返回值，
随后raw.write(data)才将字节写入已打开文件。过滤和字节转换是内存操作，不重新估计位姿。

```python
observed[cell_xy[:, 1], cell_xy[:, 0]] = True
```

第一行先减去覆盖区左下角，得到相对该边界的平面距离，再除以每格边长。
np.floor向下取整，决定点落在哪个区间，不是四舍五入；astype(np.int64)将结果转成整数索引。
cell_xy每行对应一个点，两列依次为X方向列号、Y方向行号，都从0计数。
假设origin_xy=(0,0)，resolution=0.1，点XY=(0.24,0.37)，
除法得到(2.4,3.7)，向下取整得到(2,3)，即第2列、第3行（编号从0开始）。
原点XY并没有被量化值替换，格子索引是另外计算的表示。

height/width由最大索引加1求得，表示格子行数/列数，不是房间米数。
np.zeros(...,dtype=bool)创建所有元素为False的布尔二维数组，形状为(height,width)。
第三行按NumPy数组先行后列的顺序，用cell_xy第二列当行号、第一列当列号，
将所有点落到的格子设为True。多个点同格依然True，不叠加计数。
True只代表至少一个切片点投影进来，False仍未确定，不代表可以走。
