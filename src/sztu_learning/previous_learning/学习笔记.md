## 1. ROS 2 与节点

ROS 2 是帮助机器人各部分软件协同工作的框架。节点是其中承担某项职责的软件单元。
Python 程序通过 ROS 2 提供的 `rclpy` 库使用节点等功能。

第一步曾使用以下代码，输出一次日志后退出：

```python
import rclpy
from rclpy.node import Node

rclpy.init()
node = Node('guide_learning')
node.get_logger().info('你好，展厅导览机器人！')
node.destroy_node()
rclpy.shutdown()
```

- `import rclpy`：导入库，尚未创建节点。
- `from rclpy.node import Node`：从模块中导入 `Node` 类，用它创建节点。
- `rclpy.init()`：初始化当前程序使用的 ROS 2 上下文，即管理本次 ROS 运行所需状态与资源的对象。
- `Node('guide_learning')`：创建节点，字符串指定节点在 ROS 2 中的名字。
- `node = ...`：让 Python 变量 `node` 指向创建出的节点对象。
  `node` 是变量名，`guide_learning` 是 ROS 节点名。变量改成 `robot` 后，后面要用
  `robot.get_logger()` 等写法，ROS 节点名仍可保持 `guide_learning`。
- `node.get_logger()`：取得节点的日志记录器。
- `.info('你好，展厅导览机器人！')`：输出一条普通信息日志，终端能显示文字；没有播放语音。
- `node.destroy_node()`：销毁节点，释放该节点的 ROS 2 资源；不等于删除 Python 变量名。
- `rclpy.shutdown()`：关闭 ROS 2 上下文。

执行调用用圆括号表示，括号内可传入参数。`=` 先计算右边，再让左边变量绑定到结果。
本步数据流：代码中的文字 → 节点的日志记录器 → 终端显示。

## 2. 让节点持续运行

第二步完成时的 `lesson01_node.py` 如下（第三步会将日志语句放入函数）：

```python
import rclpy
from rclpy.node import Node

rclpy.init()
node = Node('guide_learning')
node.get_logger().info('你好，展厅导览机器人！')

try:
    rclpy.spin(node)
except KeyboardInterrupt:
    pass
finally:
    node.destroy_node()
    rclpy.try_shutdown()
```

- `rclpy.spin(node)`：等待并处理节点的待办工作；本步没有添加业务回调，主要是在等待。
  它是阻塞调用，尚未结束时后面的语句不能继续执行。这里的 spin 不表示机器人旋转。
- 日志语句在 spin 前面，只执行一次。spin 不会重新执行文件前面的代码。
- `try:`：执行下面缩进的代码，并准备处理异常。
- `except KeyboardInterrupt:`：处理键盘中断；在终端按 `Ctrl+C` 可以触发它。
- `pass`：空语句，在这里不额外执行操作。
- `finally:`：离开这个 try 结构时执行清理。正常返回或通过异常离开都会经过这里；
  强制杀死进程、断电等不保证清理代码执行。
- `rclpy.try_shutdown()`：上下文还没关闭就关闭，已经关闭则不再重复关闭。
  ROS 2 可能在收到中断信号时已关闭上下文，因此这里使用它完成清理。
- 冒号与缩进划分 Python 代码块，表示语句属于哪个分支。

执行过程：创建节点 → 输出一次日志 → spin 等待 → Ctrl+C → 清理并退出。

复述反馈：学习者已正确说明 spin 不会立刻进入清理、前面的日志不会重复执行，
以及两条清理语句分别针对节点和 ROS 上下文。

## 3. 运行前的终端命令

这些是 Bash 终端命令，不写进 Python 文件。每行按 Enter 执行一次。

```bash

```

### source /opt/ros/humble/setup.bash

- `source` 是 Bash 内置命令：在当前终端的 shell 中执行指定脚本。
- `/opt/ros/humble/setup.bash` 是 ROS 2 Humble 安装时提供的环境脚本，humble 是发行版名称。
- 脚本设置查找命令、Python 模块和运行库等所需的环境变量，让后续程序能找到 ROS 2。
- 这里是加载已经安装的 ROS 环境，没有安装 ROS，也没有启动节点。
- 需要在当前 shell 中加载，后面启动的 Python 程序才能继承这些环境设置。

### export ROS_DOMAIN_ID=42

- `export` 是 Bash 内置命令，将变量设为环境变量，让随后从此终端启动的程序继承它。
- `ROS_DOMAIN_ID` 是 ROS 2 使用的环境变量名；`42` 是选用的域编号，无单位。
- 域可以理解成 ROS 通信分组：不同域的节点通常不会自动发现、直接通信。
  相同域只是通信的前提之一，不代表一定能够通信。
- 42 是本项目学习/仿真使用的编号，不是节点数量，也不是速度。
  项目约定真机常使用域 0，学习使用 42 避免混到同一个域。
- Bash 赋值时等号两侧不加空格。

### export ROS_LOCALHOST_ONLY=1

- 同样用 export 设置环境变量，`ROS_LOCALHOST_ONLY` 是变量名，`1` 是启用本机通信限制的值。
- 在当前 ROS 2 Humble 环境中，它将随后启动的 ROS 程序的通信限制在本机，
  本机不同进程仍可通信，不通过局域网与其他电脑或机器人进行 ROS 通信。
- 它不表示只允许一个节点，也不是关闭整台电脑的网络或禁止所有网络请求。

三行合起来的作用：加载 ROS 2 环境 → 选择域 42 → 限制 ROS 通信在本机。
最后 `python3` 调用 Python 3 解释器，后面的绝对路径指定要执行的源代码文件。

这些环境设置作用于当前终端及其后续启动的子进程，不会自动改变其他终端或已经运行的程序。
关闭终端后，手动设置不会自动永久保存；新终端若无预配置，运行前需重新执行。

## 5. 用定时器周期性调用函数

第四步保留 `report_status` 定义，将原先手动调用的 `report_status()` 替换为：

```python
timer = node.create_timer(1.0, report_status)
```

- `create_timer` 是 ROS 2 的 Node 提供的方法；这次在已有的 `node` 上创建定时器。
- `1.0` 是浮点数，指定调用周期，单位为秒；这里约每秒调用一次。
  换成 `2.0` 会约每两秒调用一次，频率更低。定时器不保证绝对精确，系统调度等会影响实际时间。
- `report_status` 不加括号，表示把函数本身传给定时器，交给后续调度使用。
  这种交给框架、在合适时机调用的函数叫“回调函数”。
- `report_status()` 加括号则会立刻执行该函数，并把返回值作为参数传入。
  本函数返回 None，所以这样写不能得到预期的定时回调。
- `create_timer(...)` 返回定时器对象，变量 `timer` 指向它；这里没有创建第二个节点。
- 创建定时器不等于当场执行回调。后面的 `rclpy.spin(node)` 让执行器等待并执行到期的回调。
  本例进入 spin 后，大约经过一个周期会看到第一条日志，随后周期性输出。
- spin 不会重跑文件；每次重复执行的是 `report_status` 函数体。
- 如果删除 spin，本例会随即走到 finally 清理并退出，不会持续输出日志。
- 节点销毁时会清理它创建的定时器，不需要在本例另加独立定时器清理语句。
- 执行顺序：创建节点 → 定义函数 → 创建定时器 → spin 调度 → 周期性调用函数 → Ctrl+C 清理退出。
- 本步只输出日志，没有发布业务消息或播放语音。
- 复述反馈：学习者正确说明周期 3.0 表示约三秒一次，重复执行的是函数。
  对“传入函数名”补充精确表述：`report_status` 这个名字指向函数对象，
  传入的是函数本身，不是名字字符串；`report_status()` 则立即调用函数并得到返回值。

## 6. 创建并填写文字消息

第五步使用 ROS 2 提供的 String 消息。消息是一种按规定结构组织的数据，后续可用于节点间传递。
导入语句写在文件顶部，函数修改为：

```python
from std_msgs.msg import String


def report_status():
    message = String()
    message.data = '你好，展厅导览机器人！'
    node.get_logger().info(message.data)
```

- `std_msgs` 是 ROS 2 提供的常见消息包，`msg` 模块提供消息类型。
  这里的 `String` 是消息类，不是 Python 自带的 `str` 类型。
- `message = String()` 创建一个消息对象，让变量 message 指向它。
  String 消息的 `data` 字段默认是空字符串 `''`。
- `message.data` 用点号访问 message 对象里名为 data 的字段；data 是该消息类型规定的字段名。
- `message.data = '你好，展厅导览机器人！'` 将这段 Python 字符串写入消息对象的 data 字段。
  message 本身仍是消息对象，不是字符串。
- `node.get_logger().info(message.data)` 读出 data 中的文字交给日志记录器。
  日志函数收到的是字符串，不是整个消息对象。
- 数据流：String() 创建消息（data 为空）→ 写入文字 → 读取文字 → 输出日志。
- 每次定时器调用 report_status，都会创建一个新的消息对象，填写相同文字，输出一次日志。
  函数结束后没有保存该消息对象供下次使用；下次调用重新创建。
- 这一轮只创建与填写消息，还没有用发布接口发送它；不能把日志输出当作业务消息发送或接收的验证。
- package.xml 中补充 std_msgs 依赖，当前直接运行 Python 不需要构建学习包。
- 学习者已正确回答本步三道复述题：data 初始为空字符串，message 是消息对象，
  message.data 是文字，日志不能证明另一个节点收到消息。

## 7. 发布文字消息到话题

第六步在创建节点后增加：

```python
publisher = node.create_publisher(String, 'robot_status', 10)
```

在 report_status 中填好 message.data 后、输出日志前增加：

```python
publisher.publish(message)
```

- 发布者是节点用来向话题发送消息的对象，topic（话题）是有名字、用于传递某种类型消息的通道。
- create_publisher 是 Node 提供的方法；创建发布者不等于已经发送消息。
- 第一个参数 String 是消息类型本身，不写 String()，此处指定后续发送哪一种消息。
- 第二个参数 'robot_status' 是话题名字符串，不是节点名或变量名。
  本例使用默认命名空间且无重映射，对外的完整话题名为 /robot_status。
- 第三个参数 10 是 QoS 历史深度：使用 KEEP_LAST，保留最近最多 10 条的历史缓存设置。
  它不是 10 秒或 10 次/秒，也不代表只能发送 10 条。其余 QoS 使用默认设置，本步不展开。
- 返回的发布者对象由变量 publisher 指向。与 node、timer、message 是不同对象。
- publisher.publish(message) 把整个 String 消息提交给发布机制，不能换成 message.data，
  因为后者是 Python 字符串，不是该发布者要求的 String 消息对象。
- 每次定时回调都会创建、填写、发布一条消息，然后输出日志；发布后 message.data 仍是原来的文字。
- publish 返回不代表其他节点已接收，使用独立接收工具核对实际收到的数据。
- 原来的日志只用于本机显示，业务消息通过 /robot_status 传递。

终端 A 沿用原运行命令启动 lesson01_node.py。保持 A 运行，打开终端 B：

```bash

export ROS_DOMAIN_ID=42
export ROS_LOCALHOST_ONLY=1

```

- ros2 是 ROS 2 命令行工具；topic echo 订阅指定话题并在终端显示接收到的消息。
- /robot_status 是接收的话题名；std_msgs/msg/String 显式指定消息类型。
- --once 表示收到一条消息后退出，不会让终端 A 的发布节点退出。
- 终端 B 必须同样加载环境并设置通信域。命令行工具本次扮演接收方，尚未自己编写订阅节点。
- 预期输出包含 `data: 你好，展厅导览机器人！`，随后 `---` 为消息显示分隔符。
- 复述反馈：学习者正确区分节点名与话题名，并指出 create_publisher 不发送消息，
  真正发送语句为 publisher.publish(message)。
- 已澄清“打印只能打印字符串”的表述：Python 内置 print() 可以输出多种对象；
  本例使用的 rclpy 日志方法 info() 接收字符串，所以传 message.data。
  publisher.publish() 则要求符合发布者声明类型的 String 消息对象，所以传 message。

## 8. 自己编写订阅节点

第七步新增 `lesson02_subscriber.py`，导入、初始化、spin 和清理沿用已学写法，

```python
def receive_status(message):

subscription = node.create_subscription(String, 'robot_status', receive_status, 10)
```

- 接收回调中的 message 是本函数的局部变量，不是发布程序的同名变量。
  两个独立进程不共享这一个 Python 对象；接收端拿到由传输数据构造的消息对象。
- create_subscription 的四个位置参数依次为：String 消息类型、'robot_status' 话题名、
  receive_status 回调函数本身、10 条历史缓存深度（其余通信设置为默认）。
- subscription 变量指向返回的订阅对象，创建订阅不等于已经收到消息。
- 回调名不加括号：交给 ROS 2 在收到消息时调用；本例注册它时没有直接调用。
- 本例话题完整名为 /robot_status。类型与发布端一致，双方使用域 42、本机通信和兼容的默认 QoS。
- 本次没有定时器：接收回调由收到消息触发，不是接收方主动每秒调用。
  发布端约每秒发送，所以正常运行时接收端也约每秒显示一次。
- 如果没有发布者发送消息，订阅程序只等待，不会凭空打印这句文字。
- 数据流：发布端 message.data → publish → /robot_status → 接收端 message → info(message.data)。

## 18. 计算机器人到展点的直线距离

第十七步在 lesson03_waypoints.py 中导入 Python 标准库 math，
增加 robot_position = {'x': 1.0, 'y': 0.0}。这是同一 demo_map 中的假设位置，不来自定位话题。
在循环中对每个展点计算：

```python
distance = math.hypot(
    waypoint['x'] - robot_position['x'],
    waypoint['y'] - robot_position['y'],
)
```

- 两个参数依次为目标与机器人之间的 x 差、y 差，单位米，前提是坐标属于同一参考系。
- math.hypot 是 Python 标准库函数，计算 sqrt(dx² + dy²)，返回直线距离，单位仍是米。
- 对机器人展区 (2, 1)，机器人假设位置 (1, 0)：dx=1、dy=1，距离 sqrt(2)≈1.414 米。
- print 中 {distance:.2f} 只让显示保留两位小数，变量 distance 保留计算结果，未被改为 1.41。
- 同一个 robot_position 用于所有展点，并没有在循环后更新为前一个展点。

```python
def receive_odom(message):
    position = message.pose.pose.position
    node.get_logger().info(
        f'{message.header.frame_id} -> {message.child_frame_id}: '
        f'x={position.x:.2f} m, y={position.y:.2f} m, z={position.z:.2f} m'
    )


subscription = node.create_subscription(
    Odometry, '/slam/lidar_odom', receive_odom, qos_profile_sensor_data
```

### 第十八步补讲：类型、话题与字段的来源

学习者已正确说明 position.x 表示以米为单位的位置，模拟数据不能证明真实机器人位置。
但上一轮跳过术语与字段来源，学习者明确要求先补讲，不增加新功能。

- nav_msgs/msg/Odometry 是 ROS 2 标准消息类型，不是某个节点或算法。
  nav_msgs 是消息包，Odometry 是其中的消息定义，在 Python 中导入同名消息类。
  里程计指随时间估计运动与位姿；Odometry 容器规定如何组织位姿、速度、时间与参考系等数据，
  它本身不进行估计。odom 也常用作坐标系名称，但与 Odometry 类型不是同一个概念。
- /slam/lidar_odom 是人为约定的话题名（通信通道名），不是消息类型或内置定位功能。
  create_publisher / create_subscription 使用这个名字建立相应通信端点，名字不会自己产生数据。
- 参考工程 lio_odom_bridge 用它作为输出话题，订阅 FAST-LIO /Odometry，转换位姿后发布；
  学习接收程序只参照该接口独立编写，不调用原 bridge，也没有启动 FAST-LIO 或原导航包。
- receive_odom 的 message 是 ROS 接收后传进来的 Odometry 实例，不是模块或全局固定数据。
- ROS 标准定义 Odometry.pose 的类型为 PoseWithCovariance，内部有 pose 和 covariance；
  内部 pose 的类型为 Pose，内部有 position 与 orientation；position 的类型为 Point，含 x、y、z。
  所以 message.pose.pose.position 按层取得 Point 对象，而 position = ... 只是给它绑定本地变量名。
- 协方差描述估计不确定性，本步不展开数值解释；位姿（pose）包含位置和朝向，而不仅是坐标。
- Odometry.header 是 Header 对象，含 stamp（时间戳）和 frame_id（位姿参考系名字）；
  child_frame_id 是 Odometry 直接包含的字符串，指定被描述的子坐标系。
  如父 odom、子 base_link，position 表示 base_link 原点在 odom 中的坐标。
  这些名字由发布程序填写，字符串本身不会自动创建 TF 变换，也不保证数据正确。
