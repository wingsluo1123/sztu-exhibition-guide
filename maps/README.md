### 2026-10-01：FAST-LIO 没有回环，而且回放**不是确定性的**

两件事，都影响"建图能不能成"这个判断，都是实测的。

**1. 这里的 FAST-LIO2 是纯里程计，没有回环、没有位姿图。**
`src/fast_lio/` 22 个源文件里 `loop_clos` / `pose_graph` / `gtsam` /
`scan_context` 零命中（同一个 grep 能搜到 `ikdtree` / `esekf` / `kalman`，
所以不是搜了个空目录）。于是上面那些"闭环误差"**不是被纠正过的闭合**，
只是回到起点时的漂移量。漂移沿路径单调累积，永不纠正 —— 展厅比这里大，
涨的是**走的路程**，不是房间面积。

**2. 同一个包跑两遍，出来的轨迹不一样。**
`20260928_163703` 和 `20260928_165013` 是同一输入（逐帧 stamp 差
0.000000000 s）、同一配置的两次回放：

| | |
|---|---|
| 逐帧位置差中位 | 0.013 m |
| p95 | 0.133 m |
| 最大 | 0.371 m（25.5 s 处开始岔开）|

机制在 `ikd_Tree.h`：`pthread_t rebuild_thread` + `Multi_Thread_Rebuild_Point_Num
1500`，后台重建赶没赶上下一次查询取决于墙上时间，近邻结果就不同，
ESEKF 更新跟着不同。**这是固有的，不是配置错了。**

后果有两条，第二条更要紧：

* **「包留着，图丢了随时能重出一张」是假的。** 重出的是另一张图，老点位
  在新图上能差 0.37 m，而到点容差只有 0.30 m。所以图必须进版本库，
  并且要能说出自己是哪一趟出的 —— 这就是 yaml 里 `sztu_lineage` 那一段，
  由 `src/sztu_slam/test/test_map_lineage.py` 盯着。
* **p95 的 0.133 m 已经是到点容差的一大块，而这还是最好的情况**（输入
  数据完全相同）。建图是一趟、讲解是另一趟，两趟的传感器数据不同，
  同一个物理位置上的差只会更大。

### 还没有数的那件事：趟与趟之间差多少

上面第二条指向一个没测过的量：**建图那趟和讲解那趟，在同一个物理位置上
的坐标差多少。** 这个数决定"建一次图、以后照着走"这条路成不成立，
而目前**一个样本都没有**。

本机 9 趟 run 都不能用来估它：5 趟路径闭合但包里没 IMU、也没 bridge 日志，
重力方向只能从另一趟借（借来的假设撑不起漂移结论）；4 趟重力可信的，
机器人没走回起点，压根没有漂移可测。交集为空。

要定下来只需要一个便宜实验（要机器人动，得人来做）：

> 在测试房间走同一条路**两趟**，各出一张图，比同一个物理位置在两张图里的坐标。
>
> * 差 ≤ 0.1 m → 展厅这条路有戏
> * 差 ≥ 0.3 m → "建一次图、以后照着走"走不通，**必须要重定位**

重定位恰恰是没授权的那个厂商 SLAM 提供的（授权范围不含 `slam` /
`map_manager` / `auto_integrated`）。所以这个实验的结果直接决定
ROADMAP B4 那个授权申请是"以后再说"还是**展厅的前置条件**，
和避障同级。

### `sztu_up` 是什么，为什么不能丢

这张图是在某个重力系里摊平的。实走时 `lio_odom_bridge` 会**自己**从 IMU
静止段测一个重力方向 —— 和建图用的不一定是同一个数。两者差多少没人知道，
而且没有任何东西会报错：位姿和地图整体错开一个转角，机器人照着点位
信心十足地走进墙里，日志里一切正常。

所以实走时必须钉回同一个值：

    tools/run_lio_live.sh --bridge --map-frame maps/testroom.yaml

选点同理 —— `tools/pick_waypoints.py` 现在**读图里的 `sztu_up`**，
不自己另推一个。

校验（这张图的 `sztu_up` 来自 IMU 开头的静止段，下面两条是**独立**来路）：

| 来路 | 测的是什么 | 和 `sztu_up` 的夹角 |
|---|---|---|
| 轨迹平面 | 里程计：机器人走过的那一片的最小方差方向 | 1.93° |
| 地面 RANSAC | 雷达回波：在这张图的系里拟合地面（30.8 万点，平面厚 13 mm） | 1.71° |

三条路是三种物理量（加速度计 / 里程计 / 雷达回波），都落在 2° 以内，
这个坐标系才算立住。**注意这三个数不是"误差"**：房间地面本来就和重力
差着一点点，`gridmap.py` 取切层带是相对**拟合出的地面**算的，所以这
1.7° 不会糊出假墙（详见 `tools/gridmap.py` 的模块头注释）。对水平位置的
影响是 cos(1.7°) = 0.9996，35 m 上 1.5 cm，远在一格以下。


### 2026-09-30：上一张 testroom 图是**反着**摊平的

记在这儿，因为它错得很安静，光看图看不出来。这说的是 09-28 那趟出的图
（后来被上面这张换掉了），但栽的坑和图本身无关，换谁都会踩。

上一版的 `sztu_up` 记的是物理上的"下"。定符号的判据当时是"平面法向背着
点云重心"—— 一个**代理量**。它背后的假设是"雷达看到的东西整体在脚底板
下方"，而真实房间里不成立：胸挂雷达离地 1.02 m、离天花板 2.91 m，墙面在
雷达上方的部分是下方的两倍多，重心自然落在上方，法向于是被指到了地下。

后果比"图镜像了"重得多。`gridmap.py` 取的那层 0.25~1.80 m 是**相对拟合出
的地面**的，而在反的系里地面 RANSAC 拟合到的是**天花板**：

| | 反的（上一版） | 正确 |
|---|---|---|
| 地面拟合内点 | 116581 | 192452 |
| 占据格 | 2196（1.8%） | 6310（5.1%） |
| 净空 ≥ 0.95 m | 23636 格 | 2253 格 |

也就是说上一版取的是**天花板下方那一层**：墙都在，图看着像个正常房间，
但**家具一个都没进去**。当时选出的点位报着 3.2~3.8 m 的净空，实际贴着
家具。而那趟做的"独立校验"（轨迹平面 vs 地面 RANSAC 差 0.10°）比的是
**轴**不是**符号**，所以照样是绿的。

修法在 `tools/gridmap.py` 的 `floor_side`：判据换成物理量 —— 地面和天花板
都会在投影直方图上堆出尖峰（墙是竖的，堆不出峰），而**只有地面**落在
传感器离地的合理区间（0.2~2.0 m）里。两侧都命中或都不命中就报错，不猜。
合成测试和负对照在 `src/sztu_slam/test/test_gridmap.py`，其中一条专门
把"旧判据在这组数据上会指反"钉住。

### 2026-09-30：仓库里一度放着**另一趟**的图

和上面那条同一天，同样错得很安静，但这次错的不是图，是**配对**。

重新建图那趟（`20260930_214128_live`）在机器人上跑完，图出在机器人的
`/tmp/testroom.*`，点位也是在那张图上选的、进了版本库 —— **可图没进**。
仓库里留着的还是上一版：开发机回放 09-28 老包出的那张，原点
(-6.79, -11.10)，而点位文件里记的是 (-16.20, -17.18)。

两趟录制 = 两个 FAST-LIO 原点 + 两个重力系 = **两个坐标系**。后果是
`tools/tour_precheck.py` ——那个专门用来防"坐标系没对上"的脚本——只有一张
图可读，读的正是过期那张，于是它会在出发点给出一个看着合理、其实无意义的
结论。点位在正确的图上净空 0.96 m，在那张图上是 0.56 m，没有任何东西报错。

发现它纯属偶然：给用户写实走步骤时顺手用 `tour_precheck.describe()` 在
离线算了一遍出发点和两个点位的净空，数字和选点时印的对不上。

现在有门禁了：`src/sztu_slam/test/test_map_matches_waypoints.py` 拿
`config/waypoints.yaml` 的 `map.source` 找到 `maps/` 下的图，核对原点和
分辨率，并且**重算每个点位在那张图上的净空**，低于 0.95 m 就红。
拿过期那张图验过，两条判据都会红（报的正是 0.56 / 0.65 m）。

教训：出图和选点在机器人上做完之后，**图和点位要同一次提交进去**。
只进一半比两个都不进更危险 —— 两个都不进至少跑不起来。

### 怎么看建好的图 / 点云

三条路，按"要不要机器人"分：

**1. 已经建好的那张图 —— 什么都不需要。**

    xdg-open maps/testroom.png

`gridmap.py` 出图时顺带渲染的，就是导航真正吃的那张栅格图。读图时注意：
主体那个矩形是房间，**上方和左侧那些细长白扇形不是房间** —— 那是雷达从
门/窗打出去几十米没有回波，被极角扫描碾出来的空闲区，忽略掉。

**2. 点云 —— 要从包里拼，FAST-LIO 不自己存。**

    tools/assemble_map.py <run_dir>/odom -o /tmp/map.pcd

前提是那趟录制带了 `--map`（否则包里只有 `/Odometry`）。实测 1191 帧
1021 万点，体素 0.05 m 降到 40.8 万点 / 4.7 MB。

脚本末尾提示的 `pcl_viewer` 这台机器上没装，用 rviz2 看（remap 成配置里
已经在订的那个话题，这样不用改配置）：

    ros2 run pcl_ros pcd_to_pointcloud --ros-args \
        -p file_name:=/tmp/map.pcd -p tf_frame:=camera_init \
        -p publishing_period_ms:=1000 \
        -r /cloud_pcd:=/cloud_registered &
    rviz2 -d src/sztu_slam/rviz/live_mapping.rviz

`publishing_period_ms` 必须设：那个节点的发布者是 `Durability: VOLATILE`，
不设周期就只发一次，rviz2 后启动什么都收不到 —— 话题在、点数也打印了，
但画面是空的。

**3. 建图过程中实时看 —— 机器人在跑，rviz 开在开发机上。**

机器人上（**别**加 `--rviz`，它那边没有屏幕，rviz2 在无 DISPLAY 下是
core dump，不是报错退出）：

    tools/run_lio_live.sh --map

开发机上：

    tools/watch_lio.sh          # --check 只检查不开 rviz

rviz 可以先开着等，真机话题一上来就自己开始画。能看到实时位姿（红箭头）、
走过的轨迹、以及点云。

跨机器这条路有两道坎，`watch_lio.sh` 会逐条检查并告诉你怎么办：

| 坎 | 为什么 | 怎么办 |
|---|---|---|
| 内核接收缓冲 | 默认 `net.core.rmem_max` 208 KB < 一帧点云 801 KB，UDP 分片丢一片整帧就没了，**日志里什么都没有** | `sudo sysctl -w net.core.rmem_max=8388608` |
| 带宽 | 801 KB × 10 Hz = 64 Mbit/s，WiFi 名义 130 Mbit/s 实际只有一半 | 插网线（本机 10.0.1.2/24，机器人 10.0.1.41）；或者在 rviz 里把 CloudLive/CloudAccum 取消勾选 —— 只剩 `/Odometry` + `/path` 不到 10 KB/s，位置和轨迹照样看得见 |

两件容易误会的事：

* **rviz 里看不到 `maps/testroom` 那张图。** 没有 Map 图层，这台也没装
  `nav2_map_server`，`src/` 里没有任何发 `OccupancyGrid` 的节点。实时看到
  的"场景"是雷达此刻的点云，不是那张图。
* **看到的位置是相对本次开机起点的。** Fixed Frame 是 `camera_init`，也就是
  FAST-LIO 每次开机时机器人站的地方，和那张图的原点 (-16.20, -17.18) 没有
  对齐关系 —— FAST-LIO 这个分支没有重定位（见上面那一节）。要让位姿落在
  已有图上，目前只有"从贴胶带的同一点同朝向开机 + `--map-frame`"这条土办法。

rviz 配置是 `src/sztu_slam/rviz/live_mapping.rviz`，**不要**用
`src/fast_lio/rviz_cfg/loam_livox.rviz` —— 那个是 ROS 1 格式，rviz2 加载它
每个图层都 `failed to load`，开出来是个空窗口（窗口在、脚本照样打印 ✓，
里面什么都没有）。为什么做了哪些调整，写在那个配置的头注释里。

### 重新建图那趟要怎么录


1. 先确认机器人上**没有**别的 FAST-LIO 在跑（`pgrep -af run_lio_live`），
   有就先停掉 —— 两份会抢同一个 `/slam/lidar_odom`。
2. 起步前贴胶带标出发点和朝向，**开机前先站稳 2 秒**（转接层要拿这 2 秒
   测重力方向）。
3. 把**整个要用的区域**走一遍，不要只走一条线：选点要求"离走过的轨迹
   ≤ 1 m"，没走到的地方再空也用不上。
4. 每个想设讲解点的位置，**静止站满 10 秒**，并且朝向要对着展品 ——
   点位的位置和朝向都从这些停留段里取，比几何选点准得多。
5. 走完回到起点附近，方便估闭环误差。

第 4 条要站满 10 秒，是因为工具是这么判的（`pick_waypoints.find_dwells`）：
**整段都待在一个小圈里**（10 cm 内）且朝向散布 < 15°，才算"站住"。判据不是
"瞬时速度小" —— 以 5 cm/s 挪 12 秒能走出 0.6 m，比到点容差还大，那个位置
当点位是错的。所以是**真的不动**，不是"慢下来"。

录完之后：

    # 出图（--map 那趟现在会一起录 /tf，选点的朝向要靠它）
    tools/gridmap.py <run_dir> -o maps/testroom --slab 0.25 1.80

    # 从停留段取点位和朝向
    tools/pick_waypoints.py maps/testroom --bag <run_dir> --from-dwell \
        -o config/waypoints.yaml --render /tmp/wp.png


`--from-dwell` 选出来的点**照样要过原来那几道闸**：净空 ≥ 0.95 m、离轨迹
≤ 1 m、相邻两点直线畅通。站的位置本身离家具太近的会被丢掉并报出来 ——
上一趟（20260928）那 7 个像停留的段净空只有 0.46~0.90 m，全部被拒。

这个房间里**全部**停留点都会被拒（09-30 那趟 9 个停留段，净空 0.60~0.92 m，
一个都不到 0.95）。所以加了 `--nudge-m`：把站位挪到最近的达标处，
**朝向原样保留**。挪多少、朝哪个方向都会印出来，横向让步还会额外警告
（正对着的东西可能换了，讲解词要复核）。09-30 那趟实际用的是：

    tools/pick_waypoints.py /tmp/testroom --bag <run_dir> --from-dwell \
        --dwell-s 3 --nudge-m 1.5 -o config/waypoints.yaml

两个点分别挪了 0.21 m 和 0.05 m，净空 0.75/0.92 -> 0.96 m。
挪位置可以，**朝向不能补** —— 朝向是这趟录制唯一给得出、地图给不出的东西。

朝向走的是 `base_link`，和实走时 `lio_odom_bridge` 发的是同一个约定，
由 `src/sztu_slam/test/test_base_poses_matches_bridge.py` 钉住。包里没录
`/tf` 的话只能从"走直线时朝向≈前进方向"反推装配角，标准误 1.85° ——
起步朝向的预算一共 2°，单这一项就吃光了，所以别漏录 `/tf`。
